# Document creation and email delivery — edge-case audit

Reviewed 7 September 2026. The signature, request-size and browser-clock fixes were implemented and tested in **Megistos only**. The broader findings below are **proposals for review**, not silently applied changes. The original repository and other Salesforce orgs were not changed.

The normal workflow works, including complex signatures and all fourteen current packages. It cannot promise that every possible submission automatically produces a document and reaches an inbox: browser failures, native Web-to-Lead rejection, processing interruptions and mailbox rejection occur at different boundaries. This audit distinguishes them instead of treating “Email Sent” as a universal delivery guarantee.

## Fixes already completed

- Removed the false 18,000-character “invalid contour” guard, 24-stroke limit and silent 1,200-sample truncation. Controlled JSON/path/security checks remain.
- Added bounded contour compaction, an oversize-only dense-jitter fallback and adaptive PNG resolution. The finalized vector is also the displayed/rasterized shape; original samples remain available for editing in the browser session.
- Increased both signature fields from 32,768 to 131,072 characters. Client field budgets are 117,964 characters each, and the stricter **complete encoded POST budget is 92,160 bytes**. The same entry list drives measurement and native submission, including Unicode, Base64 escaping, grouped values and CRLF normalization.
- Added the requested small visual minimum: width **or** height of the mark must span 12 logical pixels in the 600 × 180 pad. A narrow line or arbitrary squiggle qualifies. No letter/identity classifier was added; existing saved dots are not invalidated.
- Salesforce receipt time now supplies signing time. Browser-clock text is optional and is never parsed or compared to a rejection window. Generated booking references and the declaration-date maximum no longer depend on a correct browser year.
- Versioned the changed browser asset URLs so a fresh page load does not reuse the old signature validators.

The 10% margin is useful protection around the actual transport boundary. It does not increase Salesforce capacity or prevent a service outage. It is applied to the **encoded whole request**, not only the visible signature or raw JSON. The per-field margin is mostly redundant for this endpoint but keeps the reusable capture module conservative. See [SIGNATURE-BOUNDARIES.md](SIGNATURE-BOUNDARIES.md) for exact measurements, including the 470/471-dot boundary and fidelity qualifications.

## Findings awaiting review

P1 denotes a material integrity/operational concern in the stated circumstances. P2 denotes a conditional functionality or recovery defect. Priorities do not mean that every ordinary form currently fails.

| ID / priority | Trigger and tangible effect | Proposed response | Downstream consequences |
| --- | --- | --- | --- |
| **FORM-01 / P2** | Browser denies session storage. `prepare()` throws while saving the return-page reference. **No POST, Lead, PDF or email**, despite otherwise valid inputs. Reproduced by throwing the browser storage error in the actual script harness | Make reference storage best-effort; catch storage exceptions on submit and the return page | Submission still works when storage is blocked; the return page may lack a reference unless an alternative is supplied. Never put signature/personal data in its URL |
| **FORM-02 / P2** | Native `submit()` throws after the UI was disabled. The page stays at Submitting and cannot be retried. **No document/email from that attempt**. Injection test confirms control flow; the platform-specific cause was not observed live | Catch synchronous dispatch errors, remove the temporary form and restore controls | A synchronous exception is distinguishable from a request that may already have left. Do not automatically replay ambiguous network failures; reuse the unique reference and provide recovery guidance |
| **FORM-03 / P2** | Core `forms.js` fails to load/run. The HTML submit control is enabled and the original form defaults to GET/current-page navigation. **No Web-to-Lead creation** | Keep submit disabled until required scripts and the signature module have initialized; show a useful reload/contact state | Prevents misleading navigation, but cannot generate documents while required JavaScript is unavailable. An accessible alternate submission process remains an operational choice |
| **DLV-01 / P1 for this trial's team testing** | Megistos reports `SingleEmail` **maximum 15 per day**. A quota failure happens after PDF creation. **PDF exists; email is not accepted and is not automatically retried after reset** | Monitor current allowance and manually Retry eligible Email errors after reset. Optional bounded scheduled retry with structured transient-error classification | Scheduling requires attempt ownership and stalled-job handling first, to avoid duplicate sends. A customer org's actual allowance must be measured separately |
| **DLV-02 / P2** | A job is cancelled before starting, or its failure status cannot be saved. Lead remains Received/Signature Saved/PDF Saved. Retry only accepts Error. **No further progress occurs just by waiting or refreshing** | Track job/attempt/progress state and add a guarded Resume action for confirmed inactive work | Broadening Retry without checking active jobs can create duplicate workers and email. Preserve frozen evidence; distinguish transient from permanent failures |
| **DLV-03 / P2** | Required PNG or PDF File is deleted between stages. Retry follows its still-populated ID and fails again. **No PDF when PNG is gone; no email when required PDF is gone** | Retention/restoration policy; verify artifacts before choosing a repair stage; explicit audited PDF restoration where possible | PNG Base64 has been cleared and no trusted server rasterizer exists. Permanent PNG loss needs restoration or a new signing. Regenerating a PDF must not silently overwrite the exact previously sent version/hash |
| **PUB-01 / P1 integrity** | Crafted insert omits all agreement discriminators while supplying generated status/snapshot/File fields. Normal initialization is skipped. A manufactured **Email Sent can exist with no generated PDF and no email job at all** | Sanitize generated agreement fields on every insert before the discriminator return; check File-to-record association where used | Historical imports that intentionally restore processed evidence need an explicit trusted migration route. Existing record/File access still applies; this is not a new permission grant |
| **ASYNC-01 / conditional P1** | Multiple trigger chunks in an async import, or another integrated automation, consume the one allowed child enqueue. A second enqueue rolls back that transaction | Coordinate dispatch per transaction and retain durable pending work | Must not silently drop the second batch. Review client Lead/File triggers and flows before integration. The isolated one-Lead form's one-child stages currently pass |
| **ASYNC-02 / conditional P1** | Finalizer's error update throws before it dispatches the remaining batch | Isolate diagnostic persistence from continuation with a durable fallback | A rethrown error can roll back a `finally` enqueue too. One record can remain unrecoverable; a multi-ID chain can strand later records |
| **ASYNC-03 / conditional P2** | One worker receives multiple Lead IDs; two agreements need six jobs, exceeding a default five-job Developer/Trial chain | Verify target depth and choose an intentional bounded depth/dispatcher before bulk support | Independent form submissions each use their own three-job chain. This is not a shared limit of two public submissions; Megistos's effective multi-record case remains untested |
| **PDF-01 / P1 for affected legal names** | A valid submitted Chinese character was retained in Salesforce but **omitted from the PDF**. Current generic sans-serif renderer selected Helvetica. Creation/email still succeeded with incomplete printed data | Verify a native Unicode-capable font in `Blob.toPdf`, with tests for agreed client languages and actual names | Font metrics can change wrapping/pagination; bold/italic support differs. Re-render all schedules. Existing executed PDFs must not be silently replaced |
| **PDF-02 / P2** | A 500-character uninterrupted address token stayed in PDF text data but extended outside the visible page. **PDF/email exist but some entered text cannot be read on the page** | Add controlled, renderer-tested break opportunities for unusually long merged text; preserve the original evidence | Requires agreement preview/PDF consistency and pagination tests. Do not assume modern browser `overflow-wrap` works in the native renderer or impose a handwriting restriction to solve a text-layout issue |

For PDF-01/02, both independent PDF renderers showed the problem. Escaped `<test>` and `<QA>` stayed literal text; accented Latin names and punctuation rendered. The current native PDF contained Times-Roman/Helvetica fonts and no extracted Chinese glyph. Salesforce's [Unicode-font guidance](https://help.salesforce.com/s/articleView?id=000385121&language=en_US&type=1) and [continuous-text truncation guidance](https://help.salesforce.com/s/articleView?id=000387706&language=en_US&type=1) support the proposed investigation; the exact `Blob.toPdf` fix is deliberately not claimed as tested or deployed.

## Existing decisions and what they do—and do not—cover

**PUB-06: yearly controlled releases.** The agreed policy is to take the form down, drain pending applications, update and test the whole release, then reopen it; do not change terms mid-season. A stale browser tab or pending Signature stage carrying an old version/hash can otherwise fail before a PDF is created. After the Signature stage freezes HTML, later PDF/email stages use that snapshot. An existing completed PDF does not change when configuration changes. Exceptional old submissions will be handled manually as requested. This finding is about agreement versions, not merely email text or a delayed “sent” label.

**PUB-02 and PLAT-01: developer-maintained releases.** Current prices and every current package combination passed. A future fee/year change still needs coordinated configuration, inherited form literals, metadata picklist values, tests and matching browser/Salesforce bundle updates. The user accepts developer involvement; the walkthrough and build procedure must remain explicit about it.

**PUB-03: independent PNG/vector acceptance.** The actual converter has been tested; a server-side proof of visual identity remains intentionally out of scope. Neither representation is used as a handwriting-authenticity classifier.

**PUB-04: honeypot without CAPTCHA.** This is the requested operating choice. An unpaid submission still consumes Lead, File, async and email capacity before payment; the 15/day trial allowance makes that tangible. Payment is not checked by this workflow. No CAPTCHA was added and no anti-bot load test was performed.

**PUB-07: native acknowledgment and email acceptance.** A Web-to-Lead redirect does not prove a Lead exists. Salesforce's successful send result does not prove inbox delivery. Domain rejection, Spam, quarantine and a valid-looking mistyped recipient remain possible. The actual test emails were found in Inbox, but the earlier sender headers showed DMARC failure. Configure a client-controlled verified sender and aligned domain authentication; branding alone does not solve deliverability.

The visual minimum is a usability choice. Electronic execution in England and Wales depends on intention to authenticate and any applicable formalities; an arbitrary mark or checkbox is not automatically proof that every agreement is enforceable. See the [Law Commission's explanation](https://lawcom.gov.uk/project/electronic-execution-of-documents/). The code does not verify identity, payment, authority in fact or organiser countersigning.

## Other conditional limits and integration checks

- **Lead validation, duplicate and assignment rules:** native Web-to-Lead can reject or route a record before this project's after-insert processing. Changes in a client sandbox can therefore affect successful creation even though Megistos cases pass. Inspect the actual destination's Lead rules and test with its default Web-to-Lead user. This project itself contains no Flow; it uses an insert trigger and three Queueable stages. Existing/future flows can still interact with its Lead/File writes.
- **Record locks, validation on updates, storage exhaustion and service faults:** these can fail File or Lead writes. Catchable and finalizer paths expose errors where persistence remains possible; there is no automatic retry/reconciliation service. Do not treat all failures as a temporary email delay.
- **Lead conversion/merge/deletion:** complete delivery before these operations under the simplest policy. Earlier conversion needs native tests for update permissions, email activity targets and resulting File links. No destructive race or conversion was induced in the shared org during this review.
- **Mistyped email:** a syntactically valid address can be wrong. The frozen address is intentionally used even if staff later edit Lead.Email. A verified, audited resend-to-corrected-address feature is not implemented.
- **Concurrent repair/backfill:** the ordinary single-POST path did not produce duplicate work, but externally queuing two workers for the same Lead can race. Add ownership/locking before automating recovery.
- **Physical devices and constrained browsers:** Pointer Events pressure/touch/coalescing paths are covered in synthetic tests. Physical pen/touch hardware, browser memory exhaustion and every PDF viewer were not tested. The document component retains Open PDF as a fallback; account/File access still governs visibility.
- **Finite storage/rendering:** the request budget deliberately blocks extreme input before Salesforce's HTTP failure. Server field/JSON/PNG checks and the PDF's 3 MB application cap remain. Native outages cannot be designed away by removing validation; recovery and monitoring are needed.
- **Trial lifetime:** Megistos is an Enterprise trial, not a permanent client service. Preserve source and evidence outside its lifetime and assess the intended customer's actual API, allocations, sender and automation.

## Recommended review order and operational response

1. Decide FORM-01/02/03 and PDF-01/02: small, well-bounded changes with reproducible triggers. Unicode loss is document correctness, not cosmetic copy.
2. Address the current email allowance and sender setup before inviting a large team to submit at once.
3. Decide PUB-01 sanitation and a coherent recovery design covering DLV-02/03 and ASYNC-02. Avoid bolting on an automatic retry loop first.
4. Treat ASYNC-01/03, conversion, ordinary-user permissions and other automation as explicit sandbox-integration gates; they are not all required to demonstrate one isolated form.

Until a recovery improvement is chosen, an operator should inspect the returned reference and Lead status when an applicant has no email. If there is no Lead, investigate native intake/validation and the endpoint response. If status is Error, inspect its stage and job ID; correct the cause, then Retry when an unsent agreement is eligible. If status remains intermediate with no active job, the current UI cannot resume it; escalate for controlled developer recovery. If status is Email Sent with a real saved PDF, inspect mail logs/recipient filtering and sender authentication. Do not rewrite frozen evidence or casually mark a record sent.

An annual release should close the form, finish or explicitly account for pending records, deploy matching terms/prices/tests, publish the site, then run a real synthetic end-to-end check before reopening. This implements the accepted seasonal policy without adding a versioning framework.

No monitoring automation or broad audit fix has been installed by this report. No finite test matrix proves the absence of every possible failure; the unexecuted conditional cases and proposed regression tests are listed explicitly in the linked reviews.
